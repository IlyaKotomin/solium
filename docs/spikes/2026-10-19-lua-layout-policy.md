# Граница layout engine и Lua

Исследование форка `IlyaKotomin/solium`, upstream `stage` / `32a9f18`.
Это предложение API и стенд для проверки причин; миграция движка ещё не сделана.
Минимальная конфигурация: [`dev/lua-lab`](../../dev/lua-lab/README.md).

## Что уже находится в Lua

В `tiling.lua` уже находятся выбор режима, деревья по workspace/монитору,
политика overflow, обработка открытия/закрытия, modal/floating и размещение.
`workspaces.lua` хранит принадлежность окна и показанный на каждом мониторе
workspace. `modes.lua` переключает режимы и восстанавливает их после reload.
Переписывать этот слой на Lua заново не требуется.

Но `sol.layout.tree()` — объект Rust с уже выбранным поведением dwindle.
Данные его структуры доступны Lua преимущественно через операции высокого
уровня, а не через независимые примитивы редактирования дерева.

## Конкретные места рассогласования

### Перенос клавишей меняет принадлежность, сохраняя старый leaf

`workspaces.send` и `send_window` меняют `workspaces.of[id]`, обновляют группы
presentation и опубликованную модель. Они не удаляют окно из исходного дерева
и не вставляют в целевое. Обработчик `layout` в tiling вызывает `apply`, а не
полную сверку `adopt`. `apply` размещает leaves дерева показанного workspace.

Следствие по коду: принадлежность и дерево могут указывать на разные desk.
В самом `tiling.open_in` уже есть отдельный обход этого состояния: при overflow
на пустой workspace создаётся новое дерево, чтобы не делить tile устаревшего leaf.
Это локальная компенсация отсутствия общего пути переноса.

Probe: `lua_layout_lab_send_reconciles_tree_membership`.
Ожидание: после отправки окна 2 с workspace 1 на 2 и следующего layout исходное
дерево больше не содержит 2. Проверяется реальный userdata дерева.
Запуск в Fedora подтвердил нарушение: `contains(2) == true` вместо `false`.

### Drop выбирает целевое дерево без переноса принадлежности

`MoveGrab.motion` перемещает реальную геометрию через `space.map_element`.
После отпускания кнопки `pending_drop` передаётся в `trigger_drop`, уже вне
блокировки pointer. Это правильная защита от reentrant deadlock, её сохраняем.

Дальше `tiling` выбирает монитор из snapshot окна, удаляет id из всех деревьев
и вставляет в `tree_for(landed)`. Эта функция использует workspace, который
монитор **показывает**. `workspaces.of[id]` в drop не обновляется.

Например: окно с desk `1@DP-1` отпускают на DP-2, показывающем workspace 2.
Дерево назначения становится `2@DP-2`, а принадлежность остаётся 1.
Фильтрация visible и следующая сверка adopt получают несовместимые ответы.
У scrolling свой похожий путь drop; общий исправленный путь должен обслуживать
оба режима, а также floating и перенос из интерфейса shell.

Probe: `lua_layout_lab_cross_monitor_drop_carries_workspace`.
Он подаёт post-move snapshot непосредственно в настоящий `Scripts::dropped`,
проверяет приём окна деревом назначения и затем его workspace. Запуск в Fedora
подтвердил: дерево назначения содержит окно, а workspace остался `1` вместо `2`.
Он не воспроизводит движение pointer через Wayland и не доказывает конкретный
визуальный симптом пользовательского бага.

### Lua не получает весь цикл перемещения

Для interactive move API отправляет `drop(id, x, y)`. Нет симметричных
`move_begin`, `move_update`, `move_end`, `move_cancel` с исходным desk,
геометрией и токеном взаимодействия. Размер меняется через отдельное событие
`resize`, которое также не описывает полный жизненный цикл.

Из одного drop нельзя надёжно восстановить, откуда начался drag, что делать
после смены workspace во время grab и куда вернуть окно при отмене.
Перенос на соседний workspace по краю и предварительный показ insertion тоже
требуют обновлений и времени, а не только финальных координат.

Отдельный уже документированный дефект: `scrolling.lua` передаёт абсолютную
координату `edge_x` в `view:widen`, ожидающий приращение. Событию нужны
недвусмысленные данные, а scroller — явная установка ширины. Это upstream #122;
не следует выдавать его за заново найденный или исправленный здесь баг.

## Какие решения вынести из Rust

| Сейчас | Предлагаемая ответственность Lua | Что остаётся механизмом Rust |
|---|---|---|
| `Tiling::split_target`: target → hit → nearest | Порядок выбора цели; focused, pointer, largest, last-used | Проверка валидности id и чтение геометрии |
| `Axis::longer`, `goes_second` при insert | Ось и сторона, fixed/alternating/manual/pointer policy | Явное редактирование split и расчёт прямоугольников |
| `room_in`: длинная ось, затем другая | Какие кандидаты попробовать и что делать при нехватке места | Проверка ограничений конкретного кандидата |
| `insert_largest`: сортировка и выбор tile | Ранжирование кандидатов и стратегия overflow | Вычисление размеров и результата split |
| `Tiling::resize`: trailing seam прежде leading | Какой seam выбирает клавиша, fallback, величина шага | Поиск seam, допустимый диапазон и применение ratio |
| Scroller хранит active/focused, выбирает следующую колонку и cycling widths | Навигация, активный элемент, пресеты, consume/expel как библиотечные функции | Расчёт колонок, ограничений и viewport |

Не надо первым шагом переносить всю арифметику на Lua. Layout crate уже не
зависит от Wayland и используется preview. Его solver и constraint-тесты полезны.
Нужен дополнительный низкоуровневый API; существующие `insert` и scroller
операции сначала сохраняются как совместимые helpers.

Пример **предлагаемого, ещё не существующего** интерфейса:

```lua
local candidate = policy.choose_split(context)
local allowed = tree:can_split(candidate.target, {
    axis = candidate.axis,
    side = candidate.side,
    ratio = candidate.ratio,
    window = context.window,
    bounds = context.work_area,
    limits = context.limits,
})
if allowed then
    tree:split(candidate.target, context.window, candidate)
end
```

Ориентацию лучше называть `axis = "x" | "y"` или `side`, без двусмысленного
«vertical»: вертикальный seam делит ширину, а вертикальный stack — высоту.
Запросы нужны также для `leaf`, `parent`, `children`, `seams`, `ratio`,
перестановки и восстановления draft; иначе Lua по-прежнему может только
комбинировать встроенные алгоритмы.

## Общий путь переноса важнее количества hooks

Первая практическая перемена — одна Lua-библиотека topology/session,
которой принадлежат logical membership и активные desk. Layout-режимы
предоставляют адаптеры `detach`, `plan_insert`, `commit`, `layout`.
Дерево — структура arrangement, не независимый источник workspace membership.
`workspaces.of`, группы renderer и публикуемая для QML модель выводятся
из этой одной модели; режимы перестают напрямую менять `of`.

Клавиша, drop, action shell, overflow и migration после hotplug используют
одну операцию с явной причиной:

```lua
-- Предложение, не существующая функция sol.*.
session.move_window(id, {
    monitor = destination.monitor,
    workspace = destination.workspace,
    target = destination.window,
    operation = "insert", -- либо swap / append / float
    reason = "drop",
    interaction = drag.token,
})
```

Последовательность: проверить destination → подготовить drafts исходного и
целевого arrangement → проверить ограничения → принять перенос → обновить
membership и layout обоих desk → пересобрать presentation groups → объявить
публичную модель → применить согласованную геометрию и focus.

Важно: нынешняя очередь commands **не является транзакцией**. `sol.keep` и
userdata изменяются внутри handler, а геометрия применяется после его возврата.
Просто добавить `sol.batch` недостаточно: ошибку Lua или отказ вставки нельзя
откатывать только в Rust, оставляя уже изменённое дерево.

Первый ограниченный шаг возможен целиком в Lua: clone/draft arrangements,
проверка назначения до удаления исходного leaf и одна точка публикации.
Полная гарантия требует протокола commit: revision исходного snapshot,
валидация command plan в host, подтверждение принятия и смена ссылки на draft
только после принятия. При ошибке/устаревшем revision старое committed состояние
остаётся целым. Lua продолжает владеть политикой; Rust проверяет живые id,
числа, grab-token и выполнимость операций. Не нужно переносить в host понятия
«dwindle», «следующий workspace» или «перенести на пустой desk».

## Drag как отдельное взаимодействие

Предлагаемые события содержат token, pane id, input source, phase,
origin geometry, origin logical desk, cursor в глобальных координатах,
pointer monitor, modifiers и reason отмены. Геометрический monitor окна,
monitor курсора и выбранный target desk — разные величины; API должен
передавать их явно. Сейчас monitor окна выводится из центра его rect,
что не всегда совпадает с намерением при отпускании у границы экрана.

Lua решает, резервировать ли исходный tile во время drag, когда detach,
какую зону drop подсветить, что означает центр/край tile, нужно ли переключить
workspace после задержки и как раскладывать окна после отпускания.
Обновления можно coalesce до одного на кадр; при отсутствии подписчика остаётся
обычное перемещение floating, чтобы Lua не стал обязательным для pointer path.

Rust сохраняет проверку serial/seat и Wayland grab, доставку pointer,
координатные преобразования, scheduler и применяемые constraints. События Lua
диспетчеризуются после освобождения seat lock. End и cancel должны быть
терминальными и взаимоисключающими для token. Закрытие окна, исчезновение
монитора, lock и reload во время drag имеют явную семантику отмены; разумный
первый вариант reload — отменить drag до замены Lua VM.

Preview не должен перезаписывать настоящую раскладку. Нужен отдельный канал
presentation с владельцем: workspace shift, mode/overview и drag preview
композируются в установленном порядке. На первом этапе это соглашение Lua
с одним composition pass; затем host может обеспечить scoped ownership.
При commit очищается только drag-channel, не transform всего окна.

## Режимы как экземпляры с областью действия

`modes.lua` сейчас хранит один `current`, а tiling/scrolling сами заводят
структуры по desk и подписываются на общие события. Новый режим повторяет
проверки active, обработку dialog/close/restore и обход мониторов. Это уже Lua,
поэтому здесь нужна общая библиотека lifecycle, а не новая функция Rust на
каждый такой случай.

Полезная форма — экземпляр layout на desk, которому контроллер передаёт
`ctx` с явными окнами, bounds, membership и interaction. Контроллер выбирает
единственного автора реальной геометрии данного desk и маршрутизирует события.
Режим предоставляет операции arrangement, а не подписывает десятки глобальных
callbacks, каждый из которых должен самостоятельно понять, относится ли событие
к нему. Так можно держать scrolling на одном monitor/workspace и manual BSP на
другом, сохранив нынешнее глобальное переключение как удобную команду политики.

Overview, peek и drag preview — overlays над layout, с отдельными каналами
presentation и lifecycle. Они не становятся конкурирующими layout writers.
Состояние экземпляров хранится через версионированную схему `sol.keep`;
миграция схемы и очистка закрытых id должны быть частью lifecycle.
Эту перестройку стоит делать после общего transfer, сохраняя адаптеры текущих
режимов, чтобы не менять одновременно модель состояния и всю раскладку.

## Порядок работы

1. Зафиксировать воспроизведения и выбрать семантику drop на другом desk:
   carry в показанный desk; sticky-окно остаётся sticky; перенос клавишей
   сохраняет monitor; никаких неявных swap там, где реально выполняется split.
2. Сделать общий путь transfer в Lua и перевести на него send, send_window,
   drop двух раскладок. Удаление исходного leaf и вставка назначения проходят
   вместе. Превратить ignored probes в проходящие regression tests.
3. Добавить begin/update/end/cancel вне grab lock и transient preview.
4. Открыть explicit tree-edit/constraint API, затем перенести выбор target,
   axis/side/fallback и seam в Lua. Совместимые helpers оставить на переход.
5. Разделить scroller geometry и navigation policy. Добавить явную ширину
   вместо использования абсолютной координаты как delta.
6. Проверить режимом, которого сейчас нет: manual BSP с выбором split side,
   вставкой по краям, swap в центре, cancel и drag между workspace. Если ему
   снова нужен mode-specific Rust, граница ещё недостаточна.

Для transfer обязательны проверки обоих направлений, разных активных desk
на двух мониторах, скрытого назначения, смены workspace во время grab,
отмены после preview, закрытия source/target, rejected fit и reload/hotplug.
Sticky, modal, floating и fullscreen должны иметь явно выбранные правила.
Проверять и ownership инварианты, и видимую геометрию: один pane принадлежит
одному arrangement (либо явно floating), отсутствует в исходном дереве после
commit, публичная модель и groups соответствуют тому же committed revision.
